# US-03, US-04, and US-08: Discover, Filter, and Accept Deliveries

Source: [`requests.js`](../api/endpoints/requests.js). All routes use the `deliveries` collection despite the `/requests` URL prefix.

These routes currently have **no session authorization checks**. Courier IDs are supplied by the client. Responses use a different envelope from the other routers:

```json
{
  "statusCode": 200,
  "message": "Available delivery requests retrieved",
  "data": []
}
```

`data` is an array for lists, a delivery document for detail/acceptance, or `null` on handled errors. Documents include stored fields such as `_id`, requester/courier IDs, item, instructions, location names, tip in cents, status, and timestamps.

## US-03 and US-08: Available Deliveries and Filters

### POST `/api/v1/requests/list`

**Body:** Optional filters; `{}` lists all available deliveries.

```json
{
  "location": "Library Entrance",
  "tipMin": 100,
  "tipMax": 500,
  "sortBy": "tip",
  "sortOrder": "desc"
}
```

Only documents with `status: "open"` and an unassigned courier are returned. MongoDB's `courierId: null` match also includes missing courier fields.

- `location` matches the pickup **or** delivery location exactly for normal string input.
- `tipMin` and `tipMax` are inclusive, non-negative integer cent values. Minimum cannot exceed maximum.
- `sortBy` supports `tip` or `pickupLocation`; `sortOrder` supports `asc` or `desc` and defaults to ascending when sorting is selected.
- Without `sortBy`, no explicit sort is applied. Clear filters by sending `{}` again.

**Success — 200:** Message `Available delivery requests retrieved`, `data: [delivery, ...]`. No matches returns `[]`.

**Errors:** 400 for invalid tip bounds, unsupported sort fields, or invalid sort direction. The backend does not implement GPS-distance sorting here; that is frontend behavior using location coordinates.

## US-04: Accepting and Viewing Assigned Deliveries

### POST `/api/v1/requests/:id/accept`

`:id` is the delivery ObjectId. **Body:** `{ "courierId": "507f1f77bcf86cd799439012" }`.

One atomic database update matches the delivery ID, `status: "open"`, and no assigned courier. It sets `courierId`, changes status to `accepted`, and refreshes `updatedAt`. Competing couriers cannot both claim the same open document.

**Success — 200:** Message `Delivery request accepted`, `data` contains the updated delivery.

**Errors:** 400 for invalid delivery/courier IDs; 404 for a missing delivery; 409 when it is no longer available. Repeated acceptance also returns 409. ID format is validated, but the courier's account and session identity are not verified by this handler.

### POST `/api/v1/requests/my`

**Body:** `{ "courierId": "507f1f77bcf86cd799439012" }`.

Lists every delivery assigned to that courier, without filtering status or explicitly sorting results. This supports the courier's assigned-delivery view, including status visibility under US-05.

**Success — 200:** Message `My delivery requests retrieved`, `data: [delivery, ...]` (or `[]`). **Errors:** 400 for a missing/invalid courier ID.

### POST `/api/v1/requests/:id/detail`

**Body:** None required. `:id` is the delivery ObjectId.

Returns the full delivery document regardless of status, allowing clients to see acceptance and subsequent progress. It does not restrict reads to delivery participants.

**Success — 200:** Message `Delivery request retrieved`, `data: delivery`.

**Errors:** 400 invalid ID; 404 delivery not found.

## Shared Errors

The router's error handler returns 500 for unexpected failures, with `message: "Unable to process request"` and `data: null`. It also handles parsing failures reaching it as 400 (`Invalid JSON body`) or 413 (`Request body too large`). The application parses JSON before mounting routers, so some parsing failures use Express's default response instead.
