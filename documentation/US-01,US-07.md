# US-01 and US-07: Accounts and Student Verification

Source: [`auth.js`](../api/endpoints/auth.js).

US-01 covers registration, login, and logout. US-07 covers administrator verification. Profile and user lookup endpoints support these stories; no separate profile story was supplied.

Requests with bodies use JSON. Login creates a session cookie, which must accompany authenticated requests. Successful responses use `{ statusCode, statusMessage, content }`. User objects exclude `passwordHash` and include `_id`, email, names, `admin`, `verified`, and timestamps. IDs serialize as strings and dates as ISO strings.

Handled errors use this format:

```json
{
  "statusCode": 401,
  "statusMessage": "Unauthorized",
  "content": { "message": "Not logged in" }
}
```

## US-01: Account Access

### POST `/api/v1/auth/signup`

**Access:** Public.

**Body:**

```json
{
  "email": "student@example.edu",
  "password": "example-password",
  "firstName": "Alex",
  "lastName": "Student"
}
```

Requires all four fields, rejects an already-used email, hashes the password with bcrypt, and saves a `users` document with `admin: false` and `verified: false`. The new user is also logged in.

**Success — 201:** `statusMessage: "Created"`, `content: { user: {...} }`.

**Errors:** 400 for missing fields; 409 for an existing email. This handler does not validate university domains or implement password-strength rules.

### POST `/api/v1/auth/login`

**Access:** Public. **Body:** `{ "email": "student@example.edu", "password": "example-password" }`.

Finds the account and compares the submitted password with its bcrypt hash. Stores the user without the password hash in the session.

**Success — 200:** `statusMessage: "OK"`, `content: { user: {...} }`.

**Errors:** 401 with `content.message: "Invalid email or password"` when credentials do not match. Login does not require `verified: true`.

### POST `/api/v1/auth/logout`

**Access:** No explicit login requirement. **Body:** None required.

Destroys the session. **Success — 200:** `statusMessage: "OK"`, `content: { message: "Logged out" }`.

### GET `/api/v1/auth/me`

**Access:** Signed-in user. **Body:** None.

Returns the user stored in the current session, rather than fetching a fresh database record.

**Success — 200:** `statusMessage: "OK"`, `content: { user: {...} }`. **Errors:** 401 if not logged in.

### GET `/api/v1/auth/user/:id`

**Access:** Any signed-in user. `:id` is the target user's ObjectId.

Looks up one user and excludes the password hash. This is not limited to the caller's own profile.

**Success — 200:** `content: { user: {...} }`. **Errors:** 400 for invalid ID; 401 without login; 404 if absent.

### PATCH `/api/v1/auth/update`

**Access:** Signed-in user updating their own account.

**Body:** Any subset of `email`, `password`, `firstName`, and `lastName`, for example `{ "firstName": "Alex" }`.

Only these fields can be updated. Password changes are hashed, duplicate email changes are rejected, and `updatedAt` is refreshed. The returned profile also replaces the caller's session user.

**Success — 200:** `content: { user: {...} }` with `statusMessage: "OK"`.

**Errors:** 400 for no supported changes or empty/null change values; 401 without login; 404 for a missing account; 409 for an email in use. Password hashing occurs before the general empty-value check, so this should not be treated as a complete password-validation policy.

## US-07: Account Verification

### GET `/api/v1/auth/getUsers`

**Access:** Any signed-in user in the current implementation, not admin-only. **Body:** None.

Returns all accounts with password hashes excluded. The frontend can display accounts with `verified: false`; the endpoint itself has no pending-only filter.

**Success — 200:** `statusMessage: "OK"`, `content: { users: [...] }`. **Errors:** 401 without login.

### PATCH `/api/v1/auth/verifyUser/:id`

**Access:** Admin, checked against the caller's current database record. **Body:** None required.

Sets the selected user's `verified` field to `true` and updates its timestamp.

**Success — 200:** `content: { user: {...} }` with `verified: true` and `statusMessage: "OK"`.

**Errors:** 400 invalid ID; 401 not logged in; 403 not an admin; 404 user not found.

### PATCH `/api/v1/auth/unverifyUser/:id`

**Access:** Admin. **Body:** None required.

Sets `verified: false` and updates the timestamp. The application has no separate rejection status or rejection-reason field.

**Success — 200:** `content: { user: {...} }` with `verified: false` and `statusMessage: "OK"`.

**Errors:** 400 invalid ID; 401 not logged in; 403 not an admin; 404 user not found.

Verification changes do not refresh other users' existing session snapshots. Setting the flag alone does not enforce verified-only access across the API. Unexpected errors in this router use Express's default error handling rather than a guaranteed JSON 500 envelope.
