# US-05 and US-06: Delivery Progress and Handoff Confirmation

Sources: [`deliveries.js`](../api/endpoints/deliveries.js) and [`deliveryConfirmation.js`](../api/endpoints/deliveryConfirmation.js).

The normal status flow is `open` -> `accepted` -> `picked_up` -> `delivered`. Acceptance is documented in [US-03/US-04/US-08](US-03,US-04,US-08.md). The routes below require a login session and use `{ statusCode, statusMessage, content }`; handled errors have `content: {}`.

## US-05: Progress and Requester History

### POST `/api/v1/deliveries/pickUpDelivery`

**Access:** Assigned courier. **Body:** `{ "deliveryId": "DELIVERY_OBJECT_ID" }`.

An atomic update matches an `accepted` delivery assigned to the session user. It changes the status to `picked_up` and refreshes `updatedAt`.

**Success — 200:** Message `Delivery picked up successfully.`, with the updated delivery directly in `content`.

**Errors:** 400 invalid ID; 401 no login; 409 if the delivery is absent, assigned to someone else, or not accepted; 500 on a caught database failure. There is no separate 403/404 response for a failed pickup match.

### GET `/api/v1/deliveries/myDeliveries`

**Access:** Signed-in requester. **Body:** None.

Lists deliveries whose `requesterId` matches the session user, newest first by `createdAt`, without restricting status.

**Success — 200:** Message `Deliveries retrieved successfully.`, with an array directly in `content` (empty array if none).

**Errors:** 401 no login; 500 database failure. Couriers use `/api/v1/requests/my` for their assigned deliveries.

## US-06: Confirmation Code

### POST `/api/v1/deliveryConfirmation/generateCode`

**Access:** The delivery's requester. **Body:** `{ "deliveryId": "DELIVERY_OBJECT_ID" }`.

Generates a random six-digit string, including leading zeroes, and upserts a `confirmationCodes` document for the delivery. A new request replaces an earlier unconfirmed code. Already-confirmed deliveries cannot generate another code. There is no expiry or global uniqueness check; verification is scoped to the delivery ID.

**Success — 201:**

```json
{
  "statusCode": 201,
  "statusMessage": "Confirmation code generated successfully.",
  "content": { "deliveryId": "DELIVERY_OBJECT_ID", "code": "012345" }
}
```

**Errors:** 400 invalid ID; 401 no login; 403 wrong requester; 404 missing delivery; 409 already confirmed; 500 processing failure.

### POST `/api/v1/deliveryConfirmation/confirmCode`

**Access:** Assigned courier.

**Body:** `{ "deliveryId": "DELIVERY_OBJECT_ID", "code": "012345" }`. Send the code as a string to preserve leading zeroes.

Requires an existing, unconfirmed code and delivery status `picked_up`. The submitted code is trimmed and compared using a constant-time comparison. An update conditioned on `confirmed: false` marks the code confirmed, recording courier and time; a subsequent update changes the delivery to `delivered`.

**Success — 200:**

```json
{
  "statusCode": 200,
  "statusMessage": "Delivery confirmed successfully.",
  "content": { "deliveryId": "DELIVERY_OBJECT_ID", "confirmed": true }
}
```

**Errors:** 400 invalid ID or missing/non-string code; 401 no login **or incorrect code**; 403 wrong courier; 404 missing delivery/code record; 409 already confirmed, concurrent confirmation, or delivery not picked up; 500 processing failure.

The confirmation and delivery updates are separate writes, not a transaction. Tracking checks both delivery status and confirmation state. The current generation endpoint does not require a particular delivery status. Unexpected failures before the handlers' `try` blocks, including some missing-body errors, are not guaranteed the JSON error envelope.
