# US-12: Reports and Delivery Disputes

Source: [`disputes.js`](../api/endpoints/disputes.js).

Participants report problems with a delivery. Administrators review reports, change their status, and may remove the linked delivery post. Each route verifies the session user against the `users` collection; administrative routes also check the current `admin` flag.

Responses use `{ statusCode, statusMessage, content }`. Handled errors use `content: {}`. A dispute contains `_id`, `postId` (the delivery ID), `createdBy`, `createdByRole`, `disputedUserId`, `disputedUserRole`, `message`, `status`, `createdAt`, and `updatedAt`.

### GET `/api/v1/disputes`

**Access:** Signed-in user. **Body:** None.

Lists disputes where the caller is the creator or the reported user, newest first.

**Success — 200:** Message `Disputes retrieved successfully.`, `content: { disputes: [...] }` (empty array if none).

### GET `/api/v1/disputes/listAll`

**Access:** Admin. **Optional query parameters:**

| Parameter | Values |
| --- | --- |
| `status` | `In Review`, `No Action`, or `Resolved`; omit for all statuses. |
| `sortBy` | `newest` (default), `oldest`, `statusAsc`, or `statusDesc`. |

Example: `/api/v1/disputes/listAll?status=In%20Review&sortBy=newest`.

Returns all matching disputes and adds `postExists` to each, indicating whether its linked delivery still exists. Status sorts use newest creation time as the secondary ordering.

**Success — 200:** Message `Disputes retrieved successfully.`, `content: { disputes: [...] }`.

**Errors:** 400 invalid status/sort; 401 no valid login; 403 not an admin.

### POST `/api/v1/disputes/create`

**Access:** Requester or assigned courier on the delivery.

**Body:**

```json
{
  "postId": "DELIVERY_OBJECT_ID",
  "message": "The item was not delivered to the agreed location."
}
```

Validates the delivery ID and a trimmed message of 1–2000 characters. The backend derives both participants from the session and delivery; the client cannot choose the reported user. The other participant must exist. One report per delivery per creator is enforced with a unique index. New disputes start as `In Review`.

**Success — 201:** Message `Dispute created successfully.`, `content: { dispute: {...} }`.

**Errors:** 400 invalid ID/message; 401 no valid login; 403 not a participant; 404 delivery or reported user missing; 409 duplicate report or missing/invalid other participant.

### PUT `/api/v1/disputes/updateStatus/:id`

**Access:** Admin. `:id` is the dispute ID.

**Body:** `{ "status": "Resolved" }` (also accepts `In Review` or `No Action`).

Changes the dispute status and `updatedAt`. There is no enforced transition order.

**Success — 200:** Message `Dispute status updated successfully.`, `content: { dispute: {...} }` containing the updated document.

**Errors:** 400 invalid ID/status; 401 no valid login; 403 not an admin; 404 dispute missing.

### DELETE `/api/v1/disputes/:id/post`

**Access:** Admin. **Body:** None. `:id` is the **dispute** ID, not the delivery ID.

Looks up the dispute and permanently deletes its referenced delivery from `deliveries`. It keeps the dispute and does not automatically change its status or delete related tracking/confirmation records.

**Success — 200:** Message `Delivery post deleted successfully.`, `content: { postId: "DELIVERY_OBJECT_ID" }`.

**Errors:** 400 invalid dispute ID; 401 no valid login; 403 not an admin; 404 dispute/delivery missing; 409 invalid or absent linked post ID.

All routes return a JSON 500 with `Unable to process dispute request.` for unexpected failures. The participant list also returns 401 without a valid login.

## Current Scope Versus the Story

Reports include their reason in `message` and reference the associated delivery using `postId`; the list response does not embed the full delivery. The administrator list indicates whether that post still exists. **Resolution notes are not implemented:** status updates accept only `status`, so the story's resolution-notes requirement is not covered by a current endpoint.
